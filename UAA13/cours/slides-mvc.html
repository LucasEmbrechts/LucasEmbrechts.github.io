Qu'est-ce qu'une architecture logicielle ?

Comme le plan d'une maison

  • Définit où placer chaque chose
  • Permet le travail en équipe
  • Facilite les modifications futures
MVC est l'une des architectures les plus populaires pour les applications web

Le problème : Code "Spaghetti"

// inscription.php - MAUVAIS EXEMPLE

// Traitement du formulaire

Les problèmes de ce code

Problème Conséquence
Code mélangé Difficile de s'y retrouver (HTML + PHP + SQL)
Injection SQL Très dangereux, un hacker peut voler la BD
Duplication Si 10 pages, on copie-colle 10 fois
Difficile à tester Impossible de tester juste la validation
Travail en équipe Un designer ne peut pas toucher au HTML

La solution : MVC

Au lieu de tout mettre dans un fichier, on sépare en 3 parties

MODEL

Données

User.php

• create()

• update()

• delete()

↔

CONTROLLER

Logique

UserController.php

• register()

• login()

• validate()

↔

VIEW

Affichage

views/register.php

• HTML/CSS

• Formulaires

• Messages

Analogie : Un restaurant

VIEW = Serveur

Prend la commande du client
Apporte les plats

CONTROLLER = Chef cuisinier

Reçoit la commande
Décide quoi faire
Coordonne l'équipe

MODEL = Cuisinier / Garde-manger

Prépare les ingrédients
Stocke dans le frigo
Récupère ce qui est demandé

Règles d'or de MVC

Le Model ne connaît PAS la View

(le cuisinier ne sort jamais de sa cuisine)

La View ne parle PAS directement au Model

(le serveur ne va pas lui-même au garde-manger)

Le Controller orchestre tout

(le chef coordonne l'équipe)

Le MODEL

Gérer les données

Le Model s'occupe de tout ce qui concerne les données

  • Stockage (sauvegarder dans la BD)
  • Récupération (chercher des infos)
  • Modification (mettre à jour)
  • Suppression (effacer)
  • Validation (vérifier que c'est correct)

Structure de la classe User


<?php
class User {
    // 1. CONNEXION À LA BD
    private $conn;
    private $table_name = "users";

    // 2. PROPRIÉTÉS (colonnes de la table)
    private $id;
    private $username;
    private $email;
    private $password;

    // 3. CONSTRUCTEUR
    public function __construct($db) {
        $this->conn = $db;
    }

    // 4. GETTERS & SETTERS
    public function getId() { return $this->id; }
    public function setId($id) { $this->id = $id; }

    // 5. MÉTHODES CRUD
    public function create() { ... }
    public function getById() { ... }
    public function update() { ... }
    public function delete() { ... }
}
?>

Méthode create() - Détails


public function create() {
    // 1. PRÉPARER LA REQUÊTE SQL
    $query = "INSERT INTO " . $this->table_name . "
              SET username = :username,
                  email = :email,
                  password = :password";

    // 2. PRÉPARER (protection injection SQL)
    $stmt = $this->conn->prepare($query);

    // 3. NETTOYER LES DONNÉES (sécurité XSS)
    $this->username = htmlspecialchars(strip_tags($this->username));
    $this->email = htmlspecialchars(strip_tags($this->email));

    // 4. HASHER LE MOT DE PASSE
    $password_hash = password_hash($this->password, PASSWORD_BCRYPT);

    // 5. LIER LES PARAMÈTRES
    $stmt->bindParam(":username", $this->username);
    $stmt->bindParam(":email", $this->email);
    $stmt->bindParam(":password", $password_hash);

    // 6. EXÉCUTER
    if($stmt->execute()) {
        $this->id = $this->conn->lastInsertId();
        return true;
    }
    return false;
}

Point sécurité : Injection SQL

DANGER


// Vulnérable
$email = $_POST['email'];
// Si email = "test' OR '1'='1"

$query = "SELECT * FROM users
          WHERE email = '$email'";
// Résultat :
// SELECT * FROM users
// WHERE email = 'test' OR '1'='1'

// → Renvoie TOUS les users !

SÉCURISÉ


// Protégé
$query = "SELECT * FROM users
          WHERE email = :email";

$stmt = $conn->prepare($query);
$stmt->bindParam(":email", $email);
$stmt->execute();

// Si email = "test' OR '1'='1"
// La BD cherche littéralement
// cet email bizarre
// → Pas d'injection possible

Validation des données


public static function validate($data) {
    $errors = [];

    // Username
    if(!isset($data['username']) || strlen($data['username']) < 3) {
        $errors[] = "Le username doit contenir au moins 3 caractères";
    }

    // Email
    if(!isset($data['email']) || !filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
        $errors[] = "L'email n'est pas valide";
    }

    // Password
    if(!isset($data['password']) || strlen($data['password']) < 6) {
        $errors[] = "Le mot de passe doit contenir au moins 6 caractères";
    }

    return $errors;
}

Le CONTROLLER

La logique métier

Le Controller est le chef d'orchestre

  • Recevoir les demandes de la View
  • Valider les données reçues
  • Vérifications métier (ex: email déjà utilisé ?)
  • Appeler les Models
  • Préparer la réponse
  • Gérer les erreurs

Structure UserController


<?php
require_once __DIR__ . '/../config/Database.php';
require_once __DIR__ . '/../models/User.php';

class UserController {
    private $db;      // Connexion BD
    private $user;    // Instance du Model

    public function __construct() {
        $database = new Database();
        $this->db = $database->getConnection();

        $this->user = new User($this->db);
    }

    // Méthodes d'action
    public function register($data) { ... }
    public function login($data) { ... }
    public function getProfile($user_id) { ... }
    public function updateUser($data) { ... }
    public function deleteUser($user_id) { ... }
}
?>

Création


    // ÉTAPE 3 : CRÉATION

    $this->user->setEmail($data['email']);
    $this->user->setPassword($data['password']);

La VIEW

L'interface utilisateur

La View est la partie visuelle de l'application

  • Afficher les formulaires (HTML/CSS)
  • Récupérer les données saisies par l'utilisateur
  • Appeler le Controller approprié
  • Afficher les résultats et messages

C'est ce que l'utilisateur voit et avec quoi il interagit

Exemple : views/register.php (partie PHP)


<?php
// Si le formulaire a été soumis
if($_SERVER['REQUEST_METHOD'] === 'POST') {

    // 1. RÉCUPÉRATION DES DONNÉES du formulaire
    $data = [
        'username' => $_POST['username'],
        'email' => $_POST['email'],
        'password' => $_POST['password']
    ];

    // 2. APPEL DU CONTROLLER
    require_once __DIR__ . '/../controllers/UserController.php';
    $controller = new UserController();
    $response = $controller->register($data);

    // 3. On a maintenant $response avec success/message
}
?>

Séparation dans la View

Partie PHP (début)

  • Traitement du formulaire
  • Appel du Controller
  • Récupération de la réponse

Partie HTML (après)

  • Affichage du formulaire
  • Affichage des messages
  • Mise en forme CSS

Règle : La View ne contient PAS de logique complexe, juste de l'affichage !

Ce que la View NE DOIT PAS faire

❌ PAS de requêtes SQL

$query = "SELECT * FROM users";

❌ PAS de logique métier

if(strlen($password) < 6) {
    // validation...
}

✓ Seulement de l'affichage

<?php if(isset($message)): ?>
    <p><?= $message ?></p>
<?php endif; ?>

La View ne fait qu'afficher les données, sans les traiter

Le flux de données complet

Suivons une inscription de A à Z

Récapitulatif du flux

Composant Action
Client Envoie POST avec données
View Récupère données formulaire ($_POST), instancie Controller
Controller Valide, vérifie email via Model
Model Requête SELECT (email libre ?)
Controller Remplit User, appelle create()
Model Hash password, INSERT en BD
Database Stocke, génère ID
Model → Controller Retourne succès + ID
Controller → View Prépare réponse
View → Navigateur Génère HTML avec message de succès

Points clés du MVC

  • ✓ Séparation claire : Chaque composant a son rôle
  • ✓ Sécurité : Validation, requêtes préparées, hash
  • ✓ Traçabilité : On suit facilement le parcours d'une requête
  • ✓ Testabilité : Chaque méthode peut être testée individuellement
  • ✓ Maintenabilité : Changement de BD ? On ne touche que le Model

Erreurs à éviter

Mettre du SQL dans le Controller

→ Ça va dans le Model

Mettre du HTML dans le Controller

→ Ça va dans la View

Appeler directement le Model depuis la View

→ Passer par le Controller

Oublier la sécurité

→ Toujours requêtes préparées + hash
